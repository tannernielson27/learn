# ADR 0003 — Scoring runs server-side; clients never hold the key before reveal

- **Status:** Accepted, 2026-09-10
- **Deciders:** product owner, Claude (TPM)

## Context

Every NGN item has an answer key and a scoring rule (0/1, plus-minus, dyad/triad rationale). If the key reaches a student's browser before the instructor reveals it, anyone with dev tools can read it, and the live-session results mean nothing.

## Decision

- The scoring engine in `src/lib/ngn/scoring` is pure and runs anywhere, but in production it is only called on the server (route handler or Postgres/Edge function) that reads the key and writes `responses.score`.
- Items have separate `content` and `answer_key` columns. RLS stops students from selecting `answer_key`. The key and rationale reach students only through a host-only reveal RPC.
- Client-side scoring is allowed only in the gallery and fixture modes, which have no real students. `ItemPlayer` already strips the key outside feedback mode.
- **Amended 2026-09-13 (#88):** authoring pages are a third exception. An author (instructor or admin) may read their own org's keys, since the editors cannot work without them, and **Preview case study** in the builder scores in the author's browser. These routes sit behind `requireAuthor` and org RLS, so no student reaches them. The keyless play route (`/author/items/[id]/play`) and every student-facing payload keep the rule above, and must not reuse the builder's preview data.
- **Amended 2026-09-20 (#146):** the gallery exception now names its boundary instead of trusting one. `/gallery/**` is **disabled on the production deployment and open everywhere else**. The signal is `VERCEL_ENV`, not `NODE_ENV` — Next sets `NODE_ENV` to `production` for preview builds too, so reading it would close the gallery on previews and in CI. Those stay open deliberately: previews, CI and localhost are where the gallery is actually used — sprint demos, the Playwright screenshot and axe run, a reviewer opening a route on a phone — and none of them has a real student on it, so gating them would force the screenshot run to authenticate for no security gain.
  - **The boundary is `src/proxy.ts`, which runs before anything renders.** It matches `/gallery` and `/gallery/:path*`, calls `galleryIsAvailable()` (`src/lib/gallery/availability.ts`), and answers a bare `404` with a nine-byte text body when `VERCEL_ENV` is `production`. A 404 does not advertise that the surface exists, and an empty body has nothing in it to audit. The check sits above `updateSession`, so the gallery still pays no auth round trip in either direction — the reason the matcher had excluded it.
  - **An in-render `notFound()` was tried first and is not sufficient. Do not reach for it again.** A layout and the page beneath it render **concurrently**; `notFound()` ends the segment it is thrown in, but a page subtree that has already rendered is still serialized into the same Flight stream. The response carried a real 404 status **and** the fixtures: measured on `next dev` at 21,373 bytes with two `answerKey` objects for `/gallery/items/multiple_choice` and 30,093 bytes with six for `/gallery/case-study`, each containing literal `{"correctOptionId":"opt_a"}` values. A status code is not a boundary. The layout gate is kept as a second layer — it still `await`s `connection()` so its own answer is decided per request rather than baked into the artifact that Vercel's **Promote to Production** could ship unchanged — but it is not what holds the line. The price of that `connection()` is that `/gallery/**` is server-rendered rather than statically generated, which is accepted for a debug surface.
  - `next.config.ts` `redirects()` was rejected for the same baking reason: that function runs at build time and produces a static list, so an artifact built as a preview would carry a list with no gallery rule in it and keep serving after promotion.
  - **The guarantee is a property of the response, so that is what the check reads.** `scripts/gallery-closed.mjs` (CI: `pnpm gallery:closed`, in the `check` job after `pnpm build`) starts the built app twice and asserts on real bytes: as a preview it must serve the gallery **and** the probe must find answer keys in it — a control, so a probe that stopped seeing anything fails loudly instead of passing quietly — and as production every gallery route must answer `404` with none of `answerKey`, `correctOptionId`, `rationale`, `scoring` or `maxPoints` anywhere in the body. The build it probes is made with `VERCEL_ENV` unset and then served as production, which is exactly the promoted-preview case.
  - The faster checks around it: `src/proxy.test.ts` calls the proxy, asserts the 404 and its keyless body, asserts `updateSession` is never reached, and asserts the matcher still names the gallery; `src/app/gallery/layout.test.ts` calls the layout and asserts the second layer still refuses; `src/app/gallery/gate.test.ts` asserts every route answering on a `/gallery` URL renders inside that layout; `src/lib/gallery/availability.test.ts` covers the predicate and the path test. None of these would have caught the leak above, which is why the response-level check exists.

## Consequences

- Submissions need a network round trip before a score exists. That is acceptable for live sessions, where scores appear on reveal anyway.
- Offline practice mode, if ever built, has to be an explicit exception with its own ADR.
- When student-facing payload builders arrive (Phase 3), each ships with a test asserting it never includes `answerKey`.
